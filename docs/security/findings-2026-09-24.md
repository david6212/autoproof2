- **Whether the deployed `firestore.rules` is byte-identical to the repo's.**

  scope for a read-only scan. What was done instead: seven unauthenticated

  `transfers` 403, `plate_history` 403), plus the anonymous `services` read
  the rules predict. The shape agrees. Exact equality is unproven.

  `bonnetcheck.com` has Cloudflare Email Routing MX records
  (`route1/2/3.mx.cloudflare.net`), so mail is accepted. Whether a route for
  the `support` alias exists, and where it lands, cannot be tested without
  sending mail — which is not a read-only act. SEC-05 is the half of that
  promise that *can* be settled from the code.
- **Whether the holes in SEC-01/02/06 have been used.** That needs the
  Firestore audit log. The rules and the client code prove they are possible;
  nothing here proves they happened.
- **Firestore rules unit tests.** There is no emulator suite in this repo; the
  existing `*_rules_*_test.dart` files assert on the *text* of
  `firestore.rules`, not on its behaviour. That is why SEC-05 survived 97 test

### [SEC-01] Any signed-in account can set any garage's star rating to whatever it likes, in one write
- **severity**: high
- **confidence**: confirmed
- **where**: firestore.rules:530-560 (`match /places/{placeId}` -> `allow update`)
- **evidence**: `ratingAvg` is in the allow-list and **no clause anywhere bounds it**:
  ```
  allow update: if isSignedIn()
                && request.resource.data.diff(resource.data).affectedKeys()
                     .hasOnly(['ratingCount', 'ratingSum', 'ratingAvg',
                               'lastReviewAt', 'isHidden'])
                && request.resource.data.ratingCount <= resource.data.ratingCount + 1
                && request.resource.data.ratingCount >= 0
                && request.resource.data.ratingSum >= resource.data.ratingSum - 5
                && request.resource.data.ratingSum <= resource.data.ratingSum + 5
  ```
  A write of `{ratingAvg: 5.0}` alone leaves `ratingCount` and `ratingSum`
  untouched, so every numeric clause is satisfied by equality and
  `affectedKeys()` is `['ratingAvg']`, a subset of the allow-list. It passes.
  The client never recomputes the average from the sum — it renders the stored
  field directly:
  `lib/data/models/place.dart:143` `ratingAvg: (data['ratingAvg'] as num?)?.toDouble() ?? 0`
  `lib/presentation/screens/places/place_detail_screen.dart:186-188`
  `Text(place.ratingAvg.toStringAsFixed(1), ...)` / `StarRating(rating: place.ratingAvg, ...)`
  and the same field on the two garage cards
  (`lib/presentation/widgets/garage/my_garages_section.dart:124`,
  `lib/presentation/widgets/garage/nearby_washes_section.dart:92`).
  `places` is listable anonymously — unauthenticated Firestore REST
  `GET .../documents/places?pageSize=1` returned **200** — so every `placeId`
  is free.
- **impact**: this is the known rating hole, and it has **widened**. The rule's
  comment reasons only about looping small increments and concludes "a single
  update may move the count by at most one and the sum by at most five".
  `ratingAvg` was added to the allow-list without a matching bound, so no loop
  is needed: four writes from one free account — three to lift `ratingCount`
  past `Place.minRatingsToShow` (3), one to set `ratingAvg` — make any garage
  or car wash in the country display **5.0 stars, 3 ביקורות** with zero
  reviews behind it, or **1.0** for a competitor. No review document has to
  exist. The mitigation the comment relies on (hiding the average below three
  reviews) is defeated by the same rule that lets the count rise.
- **fix**: in `firestore.rules`, in the `places` update rule, bind the average
  to the aggregate instead of trusting it. Either (a) drop `ratingAvg` from
  the `hasOnly([...])` list and compute the average on read in
  `lib/data/models/place.dart` from `ratingSum / ratingCount` — cleanest, the
  field is pure denormalisation — or (b) keep the field and add
  `&& (request.resource.data.ratingCount == 0
        || request.resource.data.ratingAvg
           == request.resource.data.ratingSum / request.resource.data.ratingCount)`.
  Prefer (a): it removes the forgeable field rather than guarding it, and it
  also corrects any stale `ratingAvg` a past write may already have left.
- **verify**: an emulator rules test (`firebase emulators:exec`) that signs in
  as a non-author uid and asserts `update({'ratingAvg': 5.0})` on a `places`
  document is **denied**; and a widget test that a `Place` built from
  `{ratingSum: 6, ratingCount: 3, ratingAvg: 5.0}` renders `2.0`.
- **autofix**: no — option (a) changes what the client reads and needs a
  backfill decision on existing `ratingAvg` values; option (b) could refuse a
  write the installed 0.9.9 APK makes if its arithmetic rounds differently.
- **status**: fixed — 24/09. The rules now require the caller's own review to
  exist after any write that moves the aggregates (`ownReviewAfter`), which the
  installed 0.9.9 client satisfies because `saveReview` writes the review and the
  aggregate in one batch. `ratingAvg` is no longer read at all: `Place.ratingAvg`
  is derived from the sum over the count, so a forged value — including any
  already written — renders as the real one. Pinned by
  `test/place_rating_integrity_test.dart`.

### [SEC-02] Any signed-in account can permanently delete any garage from the directory, in one write
- **severity**: high
- **confidence**: confirmed
- **where**: firestore.rules:530-560 (`match /places/{placeId}` -> `allow update`)
- **evidence**: `isHidden` is in the same allow-list, and the only clause that
  mentions it is one-directional:
  ```
  // Hiding is one-way. An entry three people said does not
  // exist cannot be un-hidden by the fourth.
  && (resource.data.isHidden == false
      || request.resource.data.isHidden == true)
  ```
  A write of `{isHidden: true}` alone leaves the counts equal (so every numeric
  clause passes) and satisfies this clause via its first branch. Nothing
  requires that three reports exist. The three-report threshold lives only in
  the client — `lib/data/repositories/place_repository.dart:347-350`:
  ```
  final reports = await placeRef.collection('reports').get();
  if (reports.docs.length >= 3) {
    await placeRef.update({'isHidden': true});
  }
  ```
  and hidden places are filtered out of every directory read
  (`place_repository.dart:55` `if (!place.isHidden) results[place.id] = place;`
  and `place_repository.dart:299` `.where('isHidden', isEqualTo: false)`).
  `allow delete: if false` on the place, plus the one-way clause above, mean
  **nothing in the app or the rules can undo it** — only a console edit.
- **impact**: the rule's own comment states the design goal — "the report is
  keyed by uid so nobody can reach three by themselves". One free account
  bypasses the counter entirely and removes any garage or car wash from the
  directory, irreversibly, without leaving a single `reports` document to
  explain why. A garage owner with a grudge can clear every competitor in a
  city in one script run. There is no operator un-hide path either:
  `isOperator()` is not exempted from the one-way clause.
- **fix**: in `firestore.rules`, split `isHidden` out of the shared update
  rule. Require either the operator, or proof that the caller has at least
  filed a report:
  `&& (!('isHidden' in request.resource.data.diff(resource.data).affectedKeys())
        || isOperator()
        || exists(/databases/$(database)/documents/places/$(placeId)/reports/$(request.auth.uid)))`,
  and add a separate `allow update: if isOperator()` branch that may set
  `isHidden` back to `false`, because right now a wrong hide is permanent.
- **verify**: emulator rules test — a signed-in uid with no `reports` document
  is **denied** `update({'isHidden': true})`; the operator is **allowed**
  `update({'isHidden': false})`.
- **autofix**: no — this is a rules change that can refuse a write the
  installed 0.9.9 APK makes (`reportDoesNotExist` performs exactly this update
  from the third reporter's device), so it ships with a client change or with
  a decision to let that path fail.
- **status**: fixed — 24/09. Setting `isHidden` now requires a report document
  in the caller's own name, or the operator. `reportDoesNotExist` files that
  report before it hides, so the installed client still works. The operator is
  also exempted from the one-way clause, so a wrong removal is no longer
  permanent and console-only. Pinned by `test/place_rating_integrity_test.dart`.
  Residual, and stated plainly: the rules cannot count to three, so one account
  that files its own report can still hide one place — it now leaves a document
  with its uid on it, and it can be undone.

### [SEC-03] Service receipts — a garage invoice with a name, a plate and often an address — are readable by anyone, signed in or not
- **severity**: high
- **confidence**: confirmed
- **where**: firestore.rules:305-311 (`vehicles/{id}/services` read) +
  lib/data/repositories/storage_repository.dart:36-47 +
  lib/data/models/service_record.dart:46
- **evidence**: the receipt goes to Cloud Storage and its **download URL** —
  which carries its own access token and is served by an endpoint that does
  not consult Storage rules — is written into the service record:
  `lib/data/models/service_record.dart:46` `final String? receiptUrl; // Firebase Storage`
  `lib/presentation/providers/vehicle_provider.dart:305,329` upload, then
  `receiptUrl: receiptUrl` onto the record.
  That record is world-readable the moment the car is listed, with the
  signed-out branch evaluated **first, on purpose**:
  ```
  allow read: if vehicleData(vehicleId).isListed == true
              || (isSignedIn()
                  && vehicleData(vehicleId).ownerId == request.auth.uid);
  ```
  The chain needs no account and no app. Unauthenticated Firestore REST with
  the public web API key:
  ```
  GET .../documents/cars?pageSize=40                                -> 200, field 'vehicleId' present
  GET .../documents/vehicles/demo-vehicle-mazda                     -> 403  (the doc itself is protected)
  GET .../documents/vehicles/demo-vehicle-mazda/services?pageSize=5 -> 200, 4 records
      fields: ['addedByOwnerId','cost','createdAt','date','garageName','km','title','type']
  GET .../documents/vehicles/demo-vehicle-mazda/documents?pageSize=5 -> 403
  ```
  The demo passport happens to carry no `receiptUrl`, so the live probe proves
  the *path* rather than a live leak — but the field is written by `addService`
  and rendered to buyers at
  `lib/presentation/widgets/service_timeline.dart:198-207`, on the buyer-facing
  listing (`car_detail_screen.dart:224` -> `DocumentedHistoryCard` ->
  `ServiceTimeline`).
  This contradicts `storage.rules:62-64`, which says receipts are "Owner only,
  for the same reason: a garage invoice carries a name, a plate and often an
  address, and **no screen ever fetches one by path**". True, and beside the
  point: nobody needs the path, because the tokenised URL is in a public
  document.
- **impact**: an unauthenticated scraper walks `cars`, collects every
  `vehicleId`, reads every listed vehicle's `services`, and downloads the
  invoices. A רישיון רכב is correctly protected (the `documents` probe returns
  403); the invoice beside it is not. Unlike the Firestore-backed documents, a
  Storage token **cannot be revoked by unsharing** — `storage.rules:22-27` says
  so itself — so taking the listing down does not close it. Publishing an
  Israeli name and address to the open internet is what Google Play's User Data
  policy forbids outright, with no exception for the owner having consented.
- **fix**: two changes, both needed. (1) Stop putting a tokenised URL in a
  world-readable document: move the receipt bytes beside the document bytes,
  i.e. `vehicles/{id}/services/{serviceId}/file/blob` as a Firestore `Blob`,
  reusing `DocumentRedactor.prepare` and the `DocumentRepository` pattern, and
  delete `uploadServiceReceipt` from
  `lib/data/repositories/storage_repository.dart`. Add a `file` subcollection
  rule that mirrors only the owner half of the parent (no `isListed` branch).
  (2) Until that ships, the rules cannot project a field away, so gate the
  receipt behind the document-sharing switch the owner already understands
  rather than the listing's `isListed`.
- **verify**: an emulator rules test that a signed-out client reading
  `vehicles/{listed}/services` gets records with no `receiptUrl`; and a `curl`
  of a real receipt URL after the listing is closed, expecting 403.
- **autofix**: no — a data migration plus a storage-model change, and the
  receipts already in the bucket need a deletion decision from David.
- **status**: fixed — 26/09. The receipt is no longer a tokenised Storage
  URL in a world-readable record: the bytes moved to
  `vehicles/{id}/services/{sid}/file/blob`, owner-only with no `isListed`
  branch, resized through `DocumentRedactor` like a licence scan.
  `ServiceRecord.receiptUrl` became `hasReceipt`, `uploadServiceReceipt` was
  deleted, and the timeline only offers the receipt when the caller passes
  `onOpenReceipt` — which the buyer's copy of the widget does not. Uploads were
  off (`storageEnabled`), so there was nothing to migrate. The service RECORD
  stays readable on a listed car: that history is what a passport is for.

### [SEC-04] "Delete my account" leaves every uploaded file in Cloud Storage, and listing photos stay world-readable forever
- **severity**: high
- **confidence**: confirmed
- **where**: lib/data/repositories/account_deletion_repository.dart:75-145
- **evidence**: `deleteEverything()` deletes Firestore documents only. There is
  no `FirebaseStorage` import in the file and no call to any storage API —
  `grep -n "Storage\|storage" lib/data/repositories/account_deletion_repository.dart`
  returns no matches. Two upload paths exist and neither is reached:
  `lib/data/repositories/storage_repository.dart:21` `_storage.ref('cars/$uid/$listingId/$i.jpg')`
  `lib/data/repositories/storage_repository.dart:44` `_storage.ref('vehicles/$uid/$vehicleId/receipts/$serviceId.$ext')`
  Listing photos are **publicly readable by path**, not merely by token —
  `storage.rules:43-44`:
  ```
  match /cars/{uid}/{listingId}/{fileName} {
    allow read: if true;
  ```
  and in Storage rules `read` covers `list`, so the prefix is also a public
  directory listing, as that file's own header explains.
  The published policy says deletion is immediate and names the listing among
  what goes — `lib/core/constants/legal_docs.dart:266-269`:
  *"מחיקת החשבון ... והיא מיידית. נמחקים: המודעה שפרסמתם, תיקי הרכב שלכם על כל
  מה שתיעדתם בהם..."*. The class's own "What this deliberately does not reach"
  section lists uid-keyed documents in other people's collections and does
  **not** mention Storage at all — so this is an omission, not a disclosed
  residue.
- **impact**: a person who deletes their account is told their listing and
  their vehicle files are gone. The photos of their car — taken, routinely, on
  their driveway — stay in a bucket prefix anyone can list, and the receipts
  stay behind permanent tokens. The Firestore record that pointed at them is
  gone, which makes it worse rather than better: nothing in the app can ever
  find them again to delete them. This fails Art. 17 erasure and the Israeli
  Privacy Protection Law right the same section claims to honour, and it is
  the exact shape of gap the 29/08 subcollection fix was written to close.
- **fix**: in `lib/data/repositories/account_deletion_repository.dart`, before
  step 5, delete the user's Storage prefixes. Add
  `StorageRepository.deleteEverythingFor(uid)` that calls
  `FirebaseStorage.instance.ref('cars/$uid').listAll()` and
  `ref('vehicles/$uid').listAll()`, recurses into `prefixes`, and deletes each
  `item`. `storage.rules` already permits it (`allow delete: if isOwner(uid)`,
  and `read` covers `list` for the owner). Files before the Firestore documents
  that name them, for the same reason the Firestore half does children first:
  a partial failure otherwise leaves unreachable blobs. Then either the files
  go, or `legal_docs.dart` section 10 says they remain — they must not both
  stay and be claimed gone.
- **verify**: a test with a fake `FirebaseStorage` asserting
  `deleteEverything()` issues `listAll()` + `delete()` against `cars/{uid}` and
  `vehicles/{uid}`; manually, after deleting a test account, `curl` a
  previously-published photo URL and expect 404.
- **autofix**: no — deleting real users' files is irreversible, and David
  should decide whether to also sweep the orphans already in the bucket from
  accounts deleted before the fix.
- **status**: open

### [SEC-05] The 14-day inbox is empty by construction — no report ever appears in it
- **severity**: high
- **confidence**: confirmed
- **where**: lib/data/repositories/operator_inbox_repository.dart:106, vs
  lib/data/repositories/car_repository.dart:244,260 and
  lib/data/repositories/place_repository.dart:228
- **evidence**: the inbox query filters on a field none of the three writers
  ever sets — `operator_inbox_repository.dart:104-108`:
  ```
  return _db
      .collection(kind.collection)
      .where('handledAt', isNull: true)
      .orderBy('createdAt')
  ```
  and all three creates omit `handledAt` entirely:
  ```
  // car_repository.dart:244   note_reports
  .add({'carId':.., 'noteId':.., 'reporterUid':.., 'createdAt': FieldValue.serverTimestamp()});
  // car_repository.dart:260   data_corrections
  .add({'kind':.., 'carId':.., 'reporterUid':.., 'note':.., 'createdAt': FieldValue.serverTimestamp()});
  // place_repository.dart:228 review_reports
  .set({'placeId':.., 'reviewUid':.., 'reporterUid':.., 'note':.., 'createdAt': FieldValue.serverTimestamp()});
  ```
  `where('handledAt', isNull: true)` compiles to `handledAt == null`, and
  Firestore does not index a document for a field it does not have — so a
  document **missing** `handledAt` is never returned. The reports are written,
  are readable by the operator (`allow read: if isOperator()`), and are
  invisible in the only surface built to show them.
  The suite misses it because it asserts on source text, not behaviour —
  `test/operator_inbox_test.dart:112`:
  `expect(repo, contains("where('handledAt', isNull: true)"));`
- **impact**: this is the exact failure the repository's own header says it
  exists to end — *"A request arrived and sat there until somebody remembered
  to open the Firebase console."* Three published documents promise an answer
  within 14 days (`legal_docs.dart:273, 408, 458`), and the channel meant to
  deliver on that promise has shown nothing since it shipped. A report of a
  defamatory note, a seller's "this information is wrong" challenge, and a
  GDPR / Privacy-Protection-Law data request all land in collections the
  operator will never see a badge for. Failing to answer a data-subject
  request is an actual breach, not a missed feature.
- **fix**: write the field. In `lib/data/repositories/car_repository.dart`
  (`reportNote`, `submitCorrection`) and
  `lib/data/repositories/place_repository.dart` (`reportReview`), add
  `'handledAt': null` to each written map — the create rules validate only
  `reporterUid` / the id shape, so this is allowed, and the
  `hasOnly(['handledAt'])` update rule keeps working. Documents already
  written stay invisible, so also change the query in
  `operator_inbox_repository.dart` to `.orderBy('createdAt').limit(50)` and
  filter `handledAt == null` client-side. That reads a few more documents and
  cannot silently break again — prefer it to a console backfill.
- **verify**: a `fake_cloud_firestore` test that writes a report through
  `reportNote()` and asserts
  `OperatorInboxRepository.watch(InboxKind.noteReport)` emits it. That is the
  test the string-matching one should have been.
- **autofix**: yes — the three `'handledAt': null` additions and the
  client-side filter are self-contained and cannot lock anyone out.
- **status**: fixed
- **fix applied (2026-09-24)**: all three writers now go through
  `unansweredReport(...)`, which spells out `handledAt: null`, and `watch()`
  no longer asks the server about that field at all — `openOnly()` decides
  open/handled client-side, so the reports **already filed** (which carry no
  such key and never would) appear too, with no console backfill. The create
  rules validate only `reporterUid` / the id shape, so the extra field is
  admitted, and `hasOnly(['handledAt'])` still governs `markHandled`.
  `test/operator_inbox_delivery_test.dart` (8 tests) runs the real filter on
  the document shape the writers produced and mounts `OperatorInboxCard` to
  prove a report reaches the screen. The old source-text assertion in
  `operator_inbox_test.dart` was removed and the reason written in its place:
  it was green for the entire outage, and after the fix it went green again on
  the *comment* explaining the removal.
- **note on the suggested verification**: `fake_cloud_firestore` was **not**
  added. It answers `isNull: true` by reading the field and comparing to null,
  so a missing key matches and the fake returns the document — the test would
  have shown the inbox working while production showed nothing.

### [SEC-06] A listing's trust signals are whatever the seller writes — the rules validate nothing but `sellerId`
- **severity**: high
- **confidence**: confirmed
- **where**: firestore.rules:121-127 (`match /cars/{carId}`)
- **evidence**: the entire validation is ownership:
  ```
  allow read: if true;
  allow create: if isSignedIn()
                && request.resource.data.sellerId == request.auth.uid;
  allow update, delete: if isSignedIn()
                && resource.data.sellerId == request.auth.uid;
  ```
  Everything a buyer is asked to trust rides in that unvalidated map —
  `lib/data/models/car_model.dart:224-262` writes `govSnapshot`,
  `plateHistorySnapshot`, `govCheckedAt`, `hasDocumentedHistory`,
  `serviceCount`, `historySpanMonths`, `reviewCount` and `createdAt`. The app
  presents `govSnapshot` as the registry's own answer (`car_model.dart:35-41`:
  *"The registry's answer as it stood when this listing was published"*) and
  renders the documentation badge straight off the boolean —
  `lib/presentation/widgets/car_card_widget.dart:302`
  `if (car.hasDocumentedHistory) ...[` and
  `lib/presentation/widgets/documented_history_card.dart:47`.
  Nothing binds `govSnapshot` to data.gov.il, and nothing binds
  `hasDocumentedHistory` / `serviceCount` to a passport that actually has
  records — whereas `vehicles` **does** guard its own copy
  (firestore.rules:280-282: `serviceCount` may only hold or rise by one).
  Separately, `update` pins nothing on the incoming document, so an owner can
  rewrite `sellerId` onto another person's uid — handing them a listing they
  did not write and escaping the one-active-listing check at
  `car_repository.dart:62` — or rewrite `createdAt` and reset the retention
  clock in SEC-13.
- **impact**: the product's whole argument is that it shows official records
  rather than seller claims. Three REST writes — no app, no registry call —
  publish a listing whose "registry answer" says no open recalls, no
  structural change, never off-road, wearing the תיק מתועד badge with no
  passport behind it. A buyer who drives across the country to see that car is
  relying on a number the seller typed. This is the one substitution the

### [SEC-16] The published APK carries only v1 and v2 signatures, not v3
- **severity**: low
- **confidence**: confirmed
- **where**: the v0.8 release asset app-arm64-v8a-release.apk
- **evidence**:
  ```
  apksigner verify --print-certs --verbose app-arm64-v8a-release.apk
    Verified using v1 scheme (JAR signing): true
    Verified using v2 scheme (APK Signature Scheme v2): true
    Verified using v3 scheme (APK Signature Scheme v3): false
    Verified using v3.1 scheme (APK Signature Scheme v3.1): false
    Number of signers: 1
    Signer #1 key algorithm: RSA   key size (bits): 2048
  ```
  `minSdk` is 23 (`android/app/build.gradle:56`, confirmed in the APK itself:
  `sdkVersion:'23'`, `targetSdkVersion:'36'`).
- **impact**: two small things. v2 covers Android 7 and above, so installs
  there are fully protected; on Android 6 only the v1 JAR signature applies,
  and v1 is what CVE-2017-13156 (Janus) attacks — an attacker who can
  substitute the APK before install can prepend a DEX without breaking the
  signature. That needs sideloading a tampered file, which is exactly how this
  APK is distributed today: a GitHub release asset, not Play. Separately, no v3
  means signing-key rotation is impossible later without orphaning every
  installed user.
- **fix**: v3 is on by default for AGP when `minSdk >= 24`; it is off here
  because `minSdk = 23`. Either raise `minSdk` to 24 in
  `android/app/build.gradle` — Android 7, released 2016, and `firebase_auth`
  already forced 23, so the practical cost is near zero — which turns v3 on by
  itself, or keep 23 and set `enableV3Signing = true` on the release signing
  config.
- **verify**: rebuild, and `apksigner verify --print-certs` must print
  `Verified using v3 scheme (APK Signature Scheme v3): true` with the same
  SHA-256 `9e497c48...c2946e`.
- **autofix**: no — raising `minSdk` drops devices, which is David's call.
- **status**: fixed — 26/09. `minSdk` 23 → 24, which turns v3 signing on by
  itself. The cost is Android 6 devices (2015); the gain is that a sideloaded
  APK is no longer protected by v1 JAR signing alone on any supported device,
  and the signing key can be rotated later without orphaning every install.

## What is right

Recorded so the next scan does not spend time re-deriving it.

- **Plates stay out of the public listing, live.** `CarModel.toFirestore`
  omits `plate`, and an unauthenticated REST read of `cars` confirms it: the
  fields returned are `area, color, createdAt, demo, description, fuel, hand,
  hasDocumentedHistory, historySpanMonths, km, make, model, ownership, photos,
  price, reasonForSelling, reviewCount, sellerId, serviceCount, spec, status,
  vehicleId, year` — no plate, no VIN. `govSnapshot` carries neither
  (`gov_data_model.dart:138-174`). The plate lives in
  `cars/{id}/private/registry`, seller-only. And `PlateFormatter.digitsOnly`
  strips everything but digits before a plate is ever used as a document id,
  so `plate_history/{plate}` cannot be path-injected.
- **Vehicle licence scans are genuinely private.** An anonymous REST read of
  `vehicles/{id}/documents` returns **403** even for a listed vehicle — the
  rule's deliberate refusal to extend the guest exception to documents
  (firestore.rules:367-372) holds in production.
- **The redactor does what it claims.** `DocumentRedactor._paint` fills black
  rectangles into the pixels with `img.fillRect` and sets
  `out.exif = img.ExifData()` before re-encoding, so the boxes are burned and
  the EXIF block — including the driveway the photo was taken on — is gone.
  The original is never stored. Its documented limit, that it cannot find
  sensitive regions by itself, matches the behaviour.
- **Unsharing a document really revokes.** Document bytes live in Firestore
  (`vehicles/{id}/documents/{docId}/file/blob`), not Storage, so every read is
  re-checked against `isSharedWithBuyers` and no token survives the switch. The
  `file` rule correctly restates the parent's condition rather than relying on
  inheritance, which rules do not provide.
- **No secrets are committed, and none ever were.**
  `git log --all --diff-filter=A --name-only` shows no `.jks`,
  `key.properties`, `.env`, `.p12` or service-account JSON ever added.
  `git check-ignore -v` confirms `android/key.properties` via
  `android/.gitignore:12` and the keystore via `android/.gitignore:14:**/*.jks`;
  the root `.gitignore` covers `/build/`, `.firebase/`, `app.*.symbols` and
  `app.*.map.json`. The `AIza...` strings in `lib/firebase_options.dart` and
  `android/app/google-services.json` are Firebase client API keys, which are
  identifiers and not secrets — and the rules make them harmless: the seven
  unauthenticated REST probes show `note_reports`, `vehicles`, `users`,
  `transfers` and `plate_history` all refused with that key in hand.
- **No PII reaches analytics, and the app does no logging at all.**
  A grep for `print(`, `debugPrint(` and `developer.log(` across `lib/` returns
  **nothing**. The four custom events (`vehicle_lookup`, `guest_prompt`,
  `login_completed`, `chat_started`) carry no plate, email, phone or id, and
  every one passes a single `allowed` gate
  (`analytics_provider.dart:35-42`). The navigator observer is a do-nothing
  `NavigatorObserver` until consent is granted, so no `screen_view` fires
  before the question has been asked.
- **No cleartext anywhere.** A grep for `http://` across `lib/`, `web/` and
  `landing/` returns nothing outside XML namespaces and loopback dev origins,
  and the deployed bundle agrees — the same grep over the live
  `main.dart.js` is empty.
- **Nothing is served that should not be.** `/app/main.dart.js.map` and
  `/app/.env` both return 200 with **1,532 bytes**, byte-identical to
  `/app/index.html` — that is the SPA rewrite answering, not a real file.
  `/.env` is a 404.
- **The deployed web build is the repo's build.** `md5sum` of the live
  `/app/main.dart.js` equals the local `build/hosting/app/main.dart.js`
  (`cbb77d0aec6e729dba5db5544ca090d0`, 4,769,387 bytes), so every live
  conclusion in this report is about that build.
- **Android permissions are all justified.** `aapt dump badging` on the
  published APK lists `ACCESS_COARSE_LOCATION` (the two maps), plus
  `INTERNET`, `ACCESS_NETWORK_STATE`, `WAKE_LOCK`,
  `BIND_GET_INSTALL_REFERRER_SERVICE` and `READ_GSERVICES`, all Firebase, and
  the Flutter dynamic-receiver permission. **No AD_ID** — the three
  `tools:node="remove"` entries worked, so the manifest now matches the
  published sentence "אין בשירות פרסומות או רשתות מעקב פרסומיות". Not
  debuggable, no cleartext, and no deep-link hosts of our own.
- **Retired collections are actually shut.** `reviews`, `inspectors` and

- **Rule and code coverage agree in both directions.** Every collection the
  code touches has a rule, and every rule matches something the code touches or

- **Ownership handover holds up.** `transfers` allows `get` but not `list`, so

  to the vehicle's **current** owner — the clause without which the whole model

  operator can change only `handledAt` on a report and only `hiddenByOperator`

  written.
