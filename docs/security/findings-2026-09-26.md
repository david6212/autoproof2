### [SEC-01] A garage's star rating can still be driven to any value by one account, one write at a time
- **severity**: high
- **confidence**: confirmed
- **where**: firestore.rules:717-760 (the `places/{placeId}` update rule)
- **evidence**: the clause added on 24/09 asks only whether the caller's review *exists after* the write — never whether it is new, nor whether the aggregates match the reviews behind them:
  ```
  function ownReviewAfter(placeId) {
    return existsAfter(/databases/$(database)/documents/places/$(placeId)/reviews/$(request.auth.uid));
  }
  ```
  ```
  && request.resource.data.ratingCount <= resource.data.ratingCount + 1
  && request.resource.data.ratingSum >= resource.data.ratingSum - 5
  && request.resource.data.ratingSum <= resource.data.ratingSum + 5
  && (!request.resource.data.diff(resource.data).affectedKeys()
        .hasAny(['ratingCount', 'ratingSum', 'ratingAvg'])
      || ownReviewAfter(placeId)
      || isOperator()
      || (...))
  ```
  The sequence: write one honest review at `places/{id}/reviews/{myUid}` (`allow create` permits it, rating 1..5), then write `places/{id}` N times with `ratingCount + 1, ratingSum + 5`. Every write satisfies every clause — keys are in `hasOnly`, deltas are inside ±1 and ±5, `ownReviewAfter` is permanently true because the review document is simply still there, `isHidden` untouched, and the count rises so the decrement branch is not needed. Downwards works the same way: `ratingSum - 5` with `ratingCount` held satisfies `ratingCount >= resource.data.ratingCount`. The rule's own comment claims otherwise — *"a move of the score now has to come with the caller's own review… One account can still add its own honest star"* — and that is the gap: existence is not novelty.
  **One thing genuinely did narrow, and should not be re-reported:** the unbounded `ratingAvg` field is inert. `Place.ratingAvg` is *computed* (`lib/data/models/place.dart:98` — `ratingCount <= 0 ? 0 : ratingSum / ratingCount`) and `Place.fromFirestore` (:146-147) never reads the stored `ratingAvg`. Writing `ratingAvg: 5.0` changes nothing a user sees. The live exposure is the sum/count loop, not that field.
  `places` is empty in production right now (unauthenticated REST list, `pageSize=1`, zero documents), so no garage's score is wrong today. The write path is shipped and the rules are deployed.
- **impact**: a real business, named, with an address, gets a manufactured 5.0 or a manufactured 1.2 from one free account and a loop — `reviewCount` passes three so the average displays. The directory's whole claim is that the score came from people who went there. Driving a competitor's score down is commercial disparagement, and it is David's product that published it.
- **fix**: in `firestore.rules`, stop letting the aggregates float free of the documents beneath them. Two clauses, both expressible without a server: (1) a `ratingCount` *increase* must come with the caller's review coming into existence in this write — replace `ownReviewAfter(placeId)` on the increment path with `(!exists(/databases/$(database)/documents/places/$(placeId)/reviews/$(request.auth.uid)) && existsAfter(...))`, which is true only for a genuinely new review and cannot be replayed; (2) bind the sum delta to the rating actually written — `request.resource.data.ratingSum - resource.data.ratingSum == getAfter(/databases/$(database)/documents/places/$(placeId)/reviews/$(request.auth.uid)).data.rating` on the create path, and the same with the old rating subtracted on the edit path. `saveReview` (`place_repository.dart:136-174`) already writes both halves in one batch, so `getAfter` sees the new rating and the installed 0.9.13 client keeps passing.
- **verify**: an emulator test (SEC-24) that signs in as one non-operator account, creates a review, then asserts a second bare `update({'ratingCount': +1, 'ratingSum': +5})` is **denied**; plus the existing happy paths — create, edit 5→2, withdraw — still allowed.
- **autofix**: no — a rules change on the write every review goes through; a mistake locks every user out of rating a garage. Deploy with one review written from a real account first.
- **status**: **fixed 05/10/2026** (`7231165`, rules deployed 19:34Z and verified byte-identical via the Rules API). Exact arithmetic on both sides: a new review adds 1 and exactly its rating, an edit moves the sum by new − old, a withdrawal removes exactly the old rating; the review document cannot be written without the place moving. Also closed a wider loop not in this report: create-5 / edit-to-1 / delete netted +4. Executed in `test/rules/place_integrity.mjs`; against the pre-fix rules the forgeries went through.

### [SEC-02] Any signed-in account can remove any garage from the directory, permanently, in two writes
- **severity**: high
- **confidence**: confirmed
- **where**: firestore.rules:699-701 and :740-744, with lib/data/repositories/place_repository.dart:333-353
- **evidence**: hiding now requires a report in the caller's name — and the caller writes that report:
  ```
  function ownReport(placeId) {
    return exists(/databases/$(database)/documents/places/$(placeId)/reports/$(request.auth.uid));
  }
  ```
  ```
  && (!request.resource.data.diff(resource.data).affectedKeys()
        .hasAny(['isHidden'])
      || isOperator()
      || ownReport(placeId))
  ```
  and the report is unconditional for its own author (`firestore.rules:836-841`):
  ```
  match /places/{placeId}/reports/{reporterUid} {
    allow create: if isSignedIn()
                  && request.auth.uid == reporterUid
                  && request.resource.data.reason is string;
  ```
  Two writes: `set places/{id}/reports/{myUid} {reason: "x"}`, then `update places/{id} {isHidden: true}`. The "three strangers" threshold exists only in the client (`place_repository.dart:348-352` counts `reports.docs.length >= 3` on the device that files the third one), and a REST client does not run the client. The hide is one-way by design (`firestore.rules:755-760`) and `allow delete: if false`, so the only way back is David, by hand. `places` is empty in production today.
- **impact**: a garage or car wash disappears from the directory on one stranger's word and stays gone until the operator notices. Recovery depends on somebody complaining to David and David believing them. For a business that gets walk-in trade from the listing, that is a real loss caused by a product that promised three independent reports.
- **fix**: in `firestore.rules`, make the rule count what the client counts. Rules cannot aggregate, so move the threshold into data they *can* check: require `places` to carry `reportCount`, allow it to rise by exactly one only when `existsAfter` the caller's own report and it did not `exist` before, and allow `isHidden: true` only when `resource.data.reportCount >= 2` (this write being the third) **and** `ownReport(placeId)`. One extra field on `places` and one extra line in `reportDoesNotExist`. If that is too much change now, the interim is to take `isHidden` out of the client-writable key list entirely and route "this place does not exist" through the operator inbox like every other complaint — slower, but unabusable.
- **verify**: an emulator test asserting account A, having filed its own report, is **denied** `update({'isHidden': true})` while `reportCount < 2`; and that after three distinct uids have reported, the third is allowed.
- **autofix**: no — needs a data-model decision (a new `reportCount` field, or removing a user-facing capability) and a migration for any place already in the collection.
- **status**: **fixed 05/10/2026** (`7231165`, same deploy). `reportCount` rises by exactly one only beside a report that did not exist before the write; a report cannot be filed without moving it; `isHidden` turns true only at three. Executed in `test/rules/place_integrity.mjs`.

### [SEC-04] "Delete my account" has no Cloud Storage step at all
- **severity**: medium
- **confidence**: confirmed
- **where**: lib/data/repositories/account_deletion_repository.dart:77-140
- **evidence**: `deleteEverything()` deletes Firestore documents only. No `firebase_storage` import in the file, no call to any storage API. `lib/data/repositories/storage_repository.dart:19` still uploads to `cars/$uid/$listingId/$i.jpg`, and `storage.rules:43-45` makes that prefix world-readable *and* world-listable:
  ```
  match /cars/{uid}/{listingId}/{fileName} {
    allow read: if true;
  ```
  The published policy names the listing among what goes (`legal_docs.dart:266-269`), and the class's own "What this deliberately does not reach" section (:50-57) does not mention Storage.
  **Why this is medium and not high: there is no bucket.** `AppConfig.storageEnabled` is `false` (`app_config.dart:28`), and an unauthenticated `curl` GET of `https://firebasestorage.googleapis.com/v0/b/autoproof-8d827.firebasestorage.app/o` and of the `.appspot.com` name both return `404 {"error":{"code":404,"message":"Not Found."}}`. One request shape, unauthenticated; a 404 from this endpoint is consistent with "no bucket" rather than "bucket whose rules refuse" (which answers 403 with a permission message) — the console settles it. So no file has ever been uploaded and nothing is exposed today. The finding is the missing code path, which becomes a live disclosure the hour Storage is switched on.
- **impact**: latent today. The day the bucket is provisioned — which is on the roadmap, because listing photos depend on it — every person who deletes their account leaves the photos of their car, routinely taken on their own driveway, in a prefix anyone can list, with the Firestore record that pointed at them gone so nothing in the app can ever find them again. Art. 17 and the Israeli Privacy Protection Law right the policy claims to honour.
- **fix**: in `lib/data/repositories/storage_repository.dart` add `Future<void> deleteEverythingFor(String uid)` that calls `FirebaseStorage.instance.ref('cars/$uid').listAll()` and `ref('vehicles/$uid').listAll()`, recurses into `prefixes`, deletes each `item`, swallowing `object-not-found`. Call it from `account_deletion_repository.dart` as a new step **2**, before the Firestore documents that name the files. `storage.rules` already permits it (`allow delete: if isOwner(uid)`, and `read` covers `list` for the owner). Do it now, while there is nothing in the bucket to get wrong.
- **verify**: a test with a fake `FirebaseStorage` asserting `deleteEverything()` issues `listAll()` and `delete()` against `cars/{uid}` and `vehicles/{uid}`; after the bucket exists, delete a test account and `curl` a previously published photo URL expecting 404.
- **autofix**: no — it deletes real users' files irreversibly, and David should decide whether the same sweep runs over orphans from accounts deleted before the fix (today: none, which is the argument for doing it now).
- **status**: open

### [SEC-17] Account deletion misses the invoice image under every service record, and leaves it permanently undeletable
- **severity**: high
- **confidence**: confirmed
- **where**: lib/data/repositories/account_deletion_repository.dart:105-107
- **evidence**: `c4c5fc6` moved receipt bytes into a subcollection one level below the service record — `service_repository.dart:47-49`:
  ```
  DocumentReference<Map<String, dynamic>> _receipt(
          String vehicleId, String serviceId) =>
      _services(vehicleId).doc(serviceId).collection('file').doc('blob');
  ```
  The deletion path was not extended to match. It handles the *documents* drawer correctly, descending into `file` first (:98-104):
  ```
  for (final document in documents.docs) {
    await _deleteAll(document.reference.collection('file'));
    await document.reference.delete();
  }
  ```
  and then treats `services` as a flat collection (:105-107):
  ```
  for (final sub in const ['services', 'reminders', 'expenses']) {
    await _deleteAll(vehicle.reference.collection(sub));
  }
  ```
  Deleting a Firestore document does not touch its subcollections — the class's own docstring (:14-16) says so in bold. So `services/{sid}/file/blob` survives, and it survives *unreachably*: its rule is
  ```
  match /services/{serviceId}/file/{blobId} {
    allow read, write: if isSignedIn()
                       && vehicleData(vehicleId).ownerId == request.auth.uid;
  ```
  (`firestore.rules:381-385`) and `vehicleData(vehicleId)` is a `get()` on a vehicle document step 3 has just deleted. With the parent gone that lookup returns null, so nobody — not the user, not a fixed client, not the operator — can ever delete the blob from outside the Firebase console. That is the exact failure the docstring at :27-31 warns about, for the one subcollection it forgot.
- **impact**: a garage invoice carries a name, a plate, usually an address, and a price. The privacy policy says deletion is immediate and names "תיקי הרכב שלכם על כל מה שתיעדתם בהם" among what goes. The record goes; the picture of the invoice stays, forever, in a document only a console can reach. It is not readable by a stranger — the rule denies everyone once the parent is gone — but "nobody can read it and nobody can delete it" is retention, not erasure, and it is a promise the code does not keep.
- **fix**: in `lib/data/repositories/account_deletion_repository.dart`, replace the flat `services` sweep with the same descend-first loop the documents drawer uses:
  ```dart
  final services = await vehicle.reference.collection('services').get();
  for (final service in services.docs) {
    await _deleteAll(service.reference.collection('file'));
    await service.reference.delete();
  }
  for (final sub in const ['reminders', 'expenses']) {
    await _deleteAll(vehicle.reference.collection(sub));
  }
  ```
  `DocumentRepository.deleteDocument` is the pattern to copy.
- **verify**: extend `test/account_deletion_test.dart` with a fake Firestore holding `vehicles/v1/services/s1/file/blob` and assert it is deleted, and deleted **before** `services/s1`. The existing test already asserts this shape for `documents/*/file`, so it is a copied case.
- **autofix**: yes.
- **status**: open

### [SEC-18] A visitor's full real name is published, unauthenticated-readable, on somebody else's listing — and survives account deletion
- **severity**: high
- **confidence**: confirmed
- **where**: lib/presentation/providers/cars_provider.dart:441-452, lib/presentation/widgets/car_notes_section.dart:194, firestore.rules:231-237
- **evidence**: the note carries the author's profile name verbatim (`cars_provider.dart:441-452`):
  ```dart
  final profile = ref.read(currentUserModelProvider).valueOrNull;
  final name = (profile?.name.trim().isNotEmpty ?? false)
      ? profile!.name
      : (user.displayName?.trim().isNotEmpty ?? false)
          ? user.displayName!
          : 'מבקר';
  await ref.read(carRepositoryProvider).addNote(
        carId: carId, authorUid: user.uid, authorName: name, tags: tags);
  ```
  `CarNote.toFirestore` writes `'authorName': authorName` (`car_note_model.dart:240`), the collection is world-readable **without an account** (`firestore.rules:231-232` — `allow read: if true`), and the widget prints it in full, not initialled (`car_notes_section.dart:194` — `Text(note.authorName, ...)`). `user.displayName` for a Google sign-in is the person's real first and last name, which is the default path for every account here — phone auth and Apple are both off.
  And it outlives the account. `deleteEverything()` deletes notes only inside the loop over the user's **own** listings (`account_deletion_repository.dart:117-133` — `listings` is `cars where sellerId == uid`, and :131 filters `authorUid == uid` within it). Notes written on *other people's* cars are never reached. The class says why it is acceptable (:52-57): *"Documents this user wrote inside other people's collections… **None of them carries a name, an address or a plate.**"* — and the policy repeats the justification (`legal_docs.dart:270-272`): *"הערות ודיווחים שכתבתם על רכבים של אחרים … שניהם אינם מקושרים לחשבון חי."* Both sentences are false about this collection. The note carries the name.

### [SEC-20] The SEC-06 listing rule makes it impossible to log a service record while the car is listed
- **severity**: high
- **confidence**: likely
- **where**: firestore.rules:155-166 with lib/data/repositories/service_repository.dart:203-216
- **evidence**: `addService` writes the record, the vehicle's counters, and the live listing's denormalised copy in **one batch** (`service_repository.dart:183-217`):
  ```dart
  batch.set(serviceRef, record.toFirestore());
  batch.update(_vehicle(vehicleId), vehicleUpdate);   // serviceCount: increment(1)
  ...
  batch.update(_db.collection('cars').doc(activeCarId), {
    'vehicleId': vehicleId,
    'serviceCount': count,                            // = serviceCount + 1
    'historySpanMonths': ...,
    'hasDocumentedHistory': ...,
  });
  ```
  The `cars` update rule demands, for any write that moves those fields:
  ```
  && (claimsUnchanged(resource.data, request.resource.data)
      || claimsMatchThePassport(request.resource.data));
  ```
  ```
  function claimsMatchThePassport(d) { ...
      : (d.get('serviceCount', 0) == vehicleOf(d.vehicleId).get('serviceCount', 0) ... )
  }
  function vehicleOf(vehicleId) {
    return get(/databases/$(database)/documents/vehicles/$(vehicleId)).data;
  }
  ```
  `claimsUnchanged` is false — `serviceCount` is exactly what changed. So it falls to `claimsMatchThePassport`, which compares the listing's **new** count against `get()` on the vehicle. In Firestore rules `get()` returns the state *before* the current write or batch; `getAfter()`/`existsAfter()` are the post-write forms, and the file uses `existsAfter` elsewhere (`firestore.rules:692`) so the distinction is known here. `get()` therefore yields the old count while the listing write carries old + 1. They can never be equal, the `cars` update is denied, and a batch is atomic — so the service record and the vehicle counter go down with it. The user sees it: the failure propagates through `AsyncValue.guard` (`vehicle_provider.dart:295`) and is rendered at `add_service_screen.dart:239`. Nothing is silent, and nothing is saved.
  Marked `likely` rather than `confirmed` because there is no emulator suite here to execute it (SEC-24) and the repo's rules tests are string matches. Also conditional on the `c4c5fc6` ruleset actually being deployed — see "What could not be checked".
- **impact**: the app's signature feature — an append-only service history a buyer can read — stops working for exactly the cars that are on the market. An owner mid-sale logs a service, gets an error, and cannot record it; the history the "תיק מתועד" badge is about can no longer grow while the badge is on display. Not a disclosure, which is why it is not critical, but a shipped rule silently deleting a core guarantee, and the fix for SEC-06 is what introduced it.
- **fix**: in `firestore.rules`, make `claimsMatchThePassport` read the vehicle as it will be *after* the batch. Add
  ```
  function vehicleAfter(vehicleId) {
    return getAfter(/databases/$(database)/documents/vehicles/$(vehicleId)).data;
  }
  ```
  and use it in the claims check. Using `getAfter` on both create and update paths is correct and simpler — `getAfter` on an untouched document returns the same data as `get`, and there is no pending vehicle write at publish time. `getAfter` costs the same one read and is cached within an evaluation.
- **verify**: an emulator test (SEC-24) that lists a vehicle, commits the real `addService` batch and asserts it **succeeds**; and a second test that commits only the `cars` half, with no vehicle write beside it, and asserts it is **denied** — the guarantee SEC-06 was written for, which must survive the fix.
- **autofix**: no — a rules change on the write path every seller with a listed car uses; it needs an emulator run first rather than a deploy-and-see.
- **status**: **fixed 05/10/2026** (`999d0dd`, deployed and verified). `getAfter` instead of `get`; executed in `test/rules/service_while_listed.mjs`. The listing claim was itself forgeable through the passport counters — closed in `9d2dfdc` (`test/rules/service_count_honest.mjs`).

  ```
                && request.resource.data.diff(resource.data).affectedKeys()
                     .hasOnly(['displayName', 'town', 'areas', 'priceIls',
                               'about', 'yearsExperience',
                               'declaresInsurance', 'claimedLicence',
                               'certStatus'])
  ```
  A fresh server timestamp is a different value, so `createdAt` lands in `affectedKeys()` and `hasOnly` fails. The write is a batch with the inbox document, so both halves are refused: the profile is not updated **and** the operator is not told an application was resubmitted.
- **impact**: latent, behind a disabled flag, with an empty collection. It is here because it is a rules-versus-code contradiction in code described as tested and ready, and because the failure mode is the worst available one — a resubmitted application vanishes silently rather than erroring visibly, which is how a fourteen-day promise gets quietly broken.
- **fix**: in `lib/data/repositories/escort_repository.dart`, write `createdAt` only on a first application — read the document first, or use `if (!(await _pros.doc(uid).get()).exists) 'createdAt': FieldValue.serverTimestamp()`. Do **not** add `createdAt` to the rule's writable list: a resettable creation timestamp is the same mistake the `cars` rule froze `createdAt` to prevent.
- **verify**: an emulator test that a second `apply()` for the same uid succeeds and leaves `createdAt` unchanged.
- **autofix**: yes — one conditional in one repository method, behind a flag, with no live data.
- **status**: open

### [SEC-29] Two files describe a security model the code no longer uses
- **severity**: low
- **confidence**: confirmed
- **where**: storage.rules:7-27 and :64-72, lib/presentation/providers/cars_provider.dart:493-495
- **evidence**: `storage.rules` opens with a long explanation of a model that has been replaced:
  ```
  // **Read is not how a buyer sees a file.** A Firebase download URL carries its
  // own access token ... That token is what shows a listing photo or a shared
  // document.
  ...
  // Known limitation, deliberate: an access token, once copied, keeps working
  // until the file is deleted — unsharing hides a document in the app but does
  // not revoke a link somebody already has.
  ```
  Neither sentence is true any more. Passport documents live in Firestore (`document_repository.dart:41-43`), and unsharing **does** revoke — `firestore.rules:517-523` restates the parent's read rule on the blob, there is no token, and :496-500 requires `isSharedWithBuyers == true && isListed == true` on every read. Likewise the `receipts/` prefix at `storage.rules:64-72` is written by nothing: `uploadServiceReceipt` was deleted on 26/09. And `cars_provider.dart:493-495` says *"`data_corrections` is `allow read: if false` — no client can read it, by design"* while `firestore.rules:657` reads `allow read: if isOperator()`.
- **impact**: no exposure today. The risk is the next reader. The whole reason `storage.rules` carries that header is to stop somebody re-opening a prefix; a header that describes the wrong architecture will instead persuade the next person that Storage-with-tokens is how documents are shared, and the "known limitation, deliberate" paragraph gives them written permission to accept a revocation hole that has already been fixed.
- **fix**: rewrite the `storage.rules` header to describe what it now governs — listing photos only, public by intent, with passport documents and receipts having moved to Firestore and why — and either delete the `vehicles/{uid}/{vehicleId}/receipts/` block or mark it explicitly reserved and unused. Correct the comment at `cars_provider.dart:493-495` to say `isOperator()`. Keep the historical note about *why* the bytes moved; it is the most valuable sentence in the file.
- **verify**: `storage_rules_test.dart` extended to assert the header no longer contains "unsharing hides a document" and that no repository references the `receipts/` prefix.
- **autofix**: yes — comments and one unused rules block, no behaviour change.
- **status**: open

### [SEC-30] Attaching a receipt writes the image and is then refused the flag that makes it visible — and the error is swallowed
- **severity**: medium
- **confidence**: likely
- **where**: lib/data/repositories/service_repository.dart:57-73, firestore.rules:398-404, lib/presentation/providers/vehicle_provider.dart:320-330
- **evidence**: `setReceipt` does two writes, and the second violates the service-record update rule:
  ```dart
  await _receipt(vehicleId, serviceId).set({
    'bytes': Blob(prepared.bytes), 'width': ..., 'height': ...,
  });
  await _services(vehicleId).doc(serviceId).update({'hasReceipt': true});
  ```
  ```
  allow update: if isSignedIn()
                && vehicleData(vehicleId).ownerId == request.auth.uid
                && request.resource.data.addedByOwnerId == resource.data.addedByOwnerId
                && request.resource.data.createdAt == resource.data.createdAt
                && request.resource.data.editedAt is timestamp;
  ```
  A record written by `addService` has no `editedAt` — `ServiceRecord.toFirestore` emits it conditionally, on purpose (`service_record.dart:182-185`: *"Only when it has been edited"*). A partial `update({'hasReceipt': true})` therefore produces a document whose `editedAt` is absent, `editedAt is timestamp` is false, and the write is denied. The caller hides it (`vehicle_provider.dart:320-330`):
  ```dart
  try {
    await services.setReceipt(...);
  } catch (_) {
    // Left without a receipt; the record stands.
  }
  ```
  So the blob lands, the flag does not, nothing ever displays the receipt, and the orphaned image is also what SEC-17 fails to delete. **Unreachable today**: the attach control is gated on `if (AppConfig.storageEnabled)` (`add_service_screen.dart:347`), which is `false` — a gate that is itself now wrong, because the receipt no longer touches Cloud Storage. `likely` for the same reason as SEC-20.
- **impact**: the feature SEC-03 was fixed to make safe cannot complete, and the failure mode is the worst available one — an image of an invoice written into the database with nothing pointing at it, invisible to the owner and unreachable by the deletion path. Latent only because a stale feature flag hides the button; flipping `storageEnabled` to enable listing photos turns it on with no other change.
- **fix**: three small things. (1) In `firestore.rules`, let a `hasReceipt`-only write through without demanding an edit stamp: add `|| request.resource.data.diff(resource.data).affectedKeys().hasOnly(['hasReceipt'])` as an alternative to the `editedAt is timestamp` clause — attaching a receipt is not an edit of what the record *says*, which is what `editedAt` exists to disclose. (2) In `service_repository.dart`, write the flag **before** the blob, or better, roll both into `addService`'s batch so a refused flag cannot leave an orphan. (3) In `add_service_screen.dart:347`, stop gating the receipt control on `AppConfig.storageEnabled` — it is a Firestore write now — and update the flag's own documentation at `app_config.dart:16-18`, which still names service receipts as depending on it.
- **verify**: an emulator test that `update({'hasReceipt': true})` on a record with no `editedAt` is **allowed** while `update({'km': 999})` without `editedAt` is still **denied**; plus a test that `setReceipt` leaves no blob behind when the flag write fails.
- **autofix**: parts (2) and (3) yes. Part (1) no — a rules change, same reasoning as SEC-20, and it should be deployed with SEC-20's fix in one reviewed ruleset rather than separately.
- **status**: open

## What is right

Recorded so the next scan does not re-derive it.

**Secrets.** Nothing secret is committed. `git ls-files` matched only two test files by name. `git grep` for `-----BEGIN`, `ghp_`, `sk-…`, `xox[baprs]-` found nothing. The only `AIza` strings are Firebase **client** API keys in `lib/firebase_options.dart` and `android/app/google-services.json`, which are public identifiers by design — and the rules are what make them harmless, which is the point this report spends its first two findings on. `android/key.properties` exists on this machine and is ignored (`android/.gitignore:12`); `**/*.jks` is ignored (`:14`); no keystore is in the tree. `.gitignore` covers `/build/`, `.firebase/`, `app.*.map.json`, `app.*.symbols`, `*.keystore`.

**The plate.** Verified on the wire, not in the source: an unauthenticated REST read of `cars` returns two documents and **neither has a `plate` field**. `CarModel.toFirestore` (:232-263) omits it, it lives at `cars/{id}/private/registry` behind `carSellerId(carId) == request.auth.uid` (`firestore.rules:200-203`), and `PlateSnapshot` carries no plate because the collection is keyed by one.

**The licence scan.** `vehicles/{id}/documents/{docId}` and the blob under it both require sign-in *and* (`isSharedWithBuyers == true` and `isListed == true`) or ownership — `firestore.rules:496-500` and :517-523. The blob rule restates the parent's rather than relying on inheritance, which rules do not provide. Because the bytes are a Firestore `Blob` and not a tokenised Storage URL, **unsharing genuinely revokes**: there is no token to survive it. That closes, in code, the "known limitation" its own `storage.rules` header still describes (SEC-29).

**The redactor.** The black boxes are burned into the pixels — `img.fillRect` on a copy, then `encodeJpg` (`document_redactor.dart:152-171`) — and `out.exif = img.ExifData()` drops the EXIF block, including the coordinates of the driveway the photo was taken on. The original is never stored. What it does not promise (finding the sensitive parts by itself) is written down at :81-86 rather than implied.

**Android.** One exported component, the launcher activity, with no deep-link host and therefore no intent surface. `allowBackup="false"`, `fullBackupContent="false"`, and `data_extraction_rules.xml` excludes `root`, `file`, `database`, `sharedpref`, `external` from **both** `cloud-backup` and `device-transfer` — the second half is the one most apps miss. No `usesCleartextTraffic`, no `debuggable`. One runtime permission, `ACCESS_COARSE_LOCATION`, justified by the fuel and inspection-centre maps, with `FINE` deliberately not requested; the three advertising-ID permissions Firebase Analytics merges in are removed with `tools:node="remove"` so the manifest matches the policy sentence *"אין בשירות פרסומות"*.

**Signing.** The published APK — downloaded from the GitHub release the landing page links to, desktop-Chrome UA — is byte-identical to the local release build (`md5 0dd23f087b1dbd9c892e9974c71f095b`). `apksigner verify --verbose --print-certs` reports `v1: false, v2: true, v3: true`, one signer, `CN=OtoV`, **SHA-256 `9e497c4845192c52b12e9745605a636ec13bb6a355b0c4381da3021878c2946e`**, SHA-1 `f0192dd94a96a23f6ee8f51c4dc43064d5c8c01c` — the hash registered in `google-services.json`, so users can update and Google Sign-In works. An operator cannot edit the text of a complaint about their own product.

**Collections: rules versus code.** Every collection the code touches has a rule: `users` (+`saved`, `past_vehicles`), `cars` (+`private`, `buyer_likes`, `seller_likes`, `journeys`, `notes`), `fuel_reports/*/reports`, `chats` (+`messages`), `plate_history/*/snapshots`, `vehicles` (+`services`, `services/*/file`, `reminders`, `expenses`, `documents`, `documents/*/file`), `transfers`, `note_reports`, `review_reports`, `data_corrections`, `pro_applications`, `escort_pros`, `places` (+`reviews`, `reports`). **No collection is written without a rule.** Three rules exist for collections nothing writes — `reviews`, `inspectors`, `bookings` — and all three are `allow read, write: if false`, which is the right way to retire a collection rather than deleting its rule. The one mismatch is the collection-group query in SEC-26.
